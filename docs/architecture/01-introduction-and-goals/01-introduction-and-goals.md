## 1.1 Requirements Overview

This document records the architecture of the Yggdrasil orchestration framework — the whole repository rooted at the project directory. Yggdrasil is not an application: it is a configuration layer for OpenCode that installs agent definitions, skills, and commands into the OpenCode configuration directory and encodes an orchestration doctrine — one orchestrator (Odin) delegating to **six** role-bound specialist subagents, exchanging transient Workfiles, gated by independent review, and backed by a persistent, reviewed knowledge base (`README.md:1-498`; `agents/odin-autonomous.md:22-44`; this revision).

**Documented scope.** The entire repository: `agents/` (9 generated agent definitions after this revision), `skills/` (10 feature directories of `SKILL.md` files), `commands/yggdrasil/` (7 command definitions), `scripts/` (generators, validator, smoke tests, template sources), `config-home/` (install-side payload), `setup.sh` (installer), `docs/architecture/` (this document), and `README.md`. The OpenCode host framework, the internal workflow steps of individual skills beyond their boundary contracts, the install-side generated `capability-inventory` skill, and CI mechanics are out of scope.

**Evidence base.** The seed content (2026-09-20, `Mode: document-existing`) cites the reviewed context Workfile of that run. This revision additionally cites the requirements Workfile `01-requirements.md`, the reviewed architecture-context Workfile `02-context-architecture-eitri.md`, and direct spot-check reads performed while drafting: `scripts/generate-subagents.sh:1-175`, `scripts/validate.sh:1-140, 335-642`, `config-home/generate-capabilities.sh:1-477`, `config-home/custom-capabilities.yaml:1-24`, `scripts/odin-generator/preamble.template.md:1-26`, `scripts/odin-generator/shared-body.template.md:14-57, 150, 225`, `scripts/subagent-generator/bragi.template.md:1-46`, `scripts/subagent-generator/heimdall.template.md:1-30`, `scripts/subagent-generator/tooling.fragment.md:1-7`, `scripts/ci-smoke-subagent-generator.sh:1-82`, `scripts/ci-smoke-generator.sh:100-159`, `scripts/README.md:1-170`, `README.md:1-498`, `.github/workflows/ci.yml:1-107`, and every persisted document this delta revises.

**Revision 2026-09-20 — Designer specialist (Eitri).** Acceptance criteria in scope: **AC-1** (Odin dispatches image requests to the Designer with full context), **AC-2** (the Designer returns an image artifact plus metadata), **AC-3** (image and metadata are consumable downstream), **AC-4** (agent definition with valid frontmatter: `name`, `description`, `mode`, `temperature`, `permission`), **AC-5** (regenerated byte-identically from its template), **AC-6** (`scripts/validate.sh` passes all checks), **AC-7** (image model specified in the agent definition is the one used), **AC-8** (changing the model requires no code change and takes effect on the next dispatch), **AC-9** (README pantheon table row), **AC-10** (README mythological-identity section). One derived criterion, **AC-11** (Designer role section present in the generated capability inventory, description carried, no agent name leaked), is proposed in Appendix A because the requirements' scope item 5 ("capability inventory updated") has no owning AC.

Two requirements statements are overridden by the user's ratified constraints carried in the brief and are recorded here so no reader reconciles them alone: the agent slug is `eitri` (not `designer`), so the file is `agents/eitri.md` and the templates are `eitri.template.md` / `eitri.workflow.template.md`; and AC-7's "or overridden in custom-capabilities.yaml" is not realizable — that file is an inventory input only (`config-home/generate-capabilities.sh:272-321` reads `name`, `role`, `summary` and renders text; nothing at runtime consumes it), so the override path is decided in ADR-0009 instead.

## 1.2 Quality Goals

**Standing goals of the system** — inferred in the seed document from what the structure, permission blocks, validators, and doctrine text are visibly optimized for (derivation basis: each goal is named only where at least two independent mechanisms enforce it). They remain the goals of the whole system and are unchanged by this revision:

| Rank | Standing quality goal | What it means here | Inferred from |
| --- | --- | --- | --- |
| S1 | **Independent verification** | No output reaches the user, the project, or Memory without a review by a reviewer that did not produce it, verified against ground truth | `agents/odin-autonomous.md:237-265, 40`; `agents/brokk.md:88`; `skills/memories/odin-memory-system/SKILL.md:57` |
| S2 | **Role isolation and least privilege** | Each agent may do only what its role needs; enforced by permission blocks, skill-prefix allowlists, and validator Check 5 | `agents/odin-autonomous.md:6-19`; `agents/mimir.md:6-68`; `agents/brokk.md:6-64`; `scripts/README.md:71` |
| S3 | **Reproducibility of the definitions** | Agent files are derived artifacts; committed state is byte-identical to generator output | `scripts/README.md:70, 87-95, 105-107, 153-160` |
| S4 | **Traceability of claims** | Research, reviews, and Memories cite paths and lines; Memories carry `sources` and a lifecycle | `skills/memories/brokk-memory-curation/SKILL.md:91-110`; `agents/brokk.md:111-113` |
| S5 | **Extensibility at the install site** | Skills and custom tool grants are added in the installed configuration home without modifying the repository | `README.md:111, 118, 127, 159`; `config-home/generate-capabilities.sh`; `config-home/custom-capabilities.yaml` |

**Goals driving this revision's decisions** — adopted verbatim and in rank order from the requirements Workfile `01-requirements.md` § Quality Goals. Every options table in Appendix A scores against these four by name; §4 names a tactic for each; §10.2 turns each into scenarios (QS-9 onward).

| Rank | Quality goal | Motivation | Measurable target or scenario hint | Serves standing goal |
| --- | --- | --- | --- | --- |
| 1 | **Consistency** | Designer must integrate seamlessly into the existing pantheon without breaking established patterns or requiring special-case handling in Odin or other agents | Agent definition structure matches existing subagents byte-for-byte in shared sections; validation passes without exceptions; no agent-specific conditionals added to Odin | S2, S3 |
| 2 | **Configurability** | Image-generation models vary widely; Designer must support model swapping without code changes so teams can use their preferred or available model | Model is configurable via agent definition or install-site configuration; changing the model requires no code edits; at least two model configurations are tested (e.g., local vs. cloud) | S5 |
| 3 | **Clarity** | Users and developers must understand Designer's role, capabilities, and constraints without ambiguity | Mythological identity and role are documented; README pantheon table is complete; Designer's boundaries (what it does and does not do) are explicit | S4 |
| 4 | **Maintainability** | Designer must be maintainable alongside the existing agents, with no hidden dependencies or special cases | Designer uses the subagent generator template system; no hardcoded paths or agent-specific logic in shared code; future agents can be added by analogy | S3, S5 |
