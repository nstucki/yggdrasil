# ADR-0011: Brokk-owned `brokk-arc42-template` scaffolds the arc42 Workfile in a dedicated step before drafting; `kvasir-software-architecture` drops its template dependency

- **Status:** Accepted (user-directed)
- **Date:** 2026-09-18

## Context
Today the arc42 skeleton is a Kvasir-owned reference skill (`kvasir-arc42-template`, Strategist inventory) that `kvasir-software-architecture` loads by name before writing (its line 12), then instantiates itself: it also looks up the existing architecture document, classifies its shape, and finds the highest ADR number (its Workflow step 1) — mechanical repository work sitting inside the one specialist whose boundary says "never run a substantive investigation." Brokk already performs exactly that classification at persistence time (`brokk-architecture-persistence` steps 2–3). The user directs that (1) the template becomes Brokk-owned and (2) Brokk scaffolds the document at the start of the workflow so Kvasir needs no template dependency at all. Two design questions remain: what the Brokk skill's shape should be, and where pruning lives. Constraints: Check 5 forbids a `kvasir-*` skill from naming a `brokk-*` slug and vice versa (C-3); every Brokk session carries a standing review (C-12); Odin doctrine names skill + inputs + Workfile, never method (repo convention, `odin-engineering-workflow` line 14). Goals: Doctrine Minimization, Cost Proportionality, Clarity of Intent, Backward Compatibility.

## Options Considered
| Option | Pros | Cons | Doctrine Min. | Cost Prop. | Clarity | Backward Compat. |
| --- | --- | --- | --- | --- | --- | --- |
| A. Status quo: Kvasir loads the template and instantiates it — **Rejected (user-directed)** | No extra dispatch | Skeleton mechanics and repo look-up inside the judgment skill; Kvasir skill depends on a template skill | 0 | + | 0 | + |
| B. Rename to `brokk-arc42-template`; the skill keeps only the § Skeleton payload as reference; `odin-architecture-workflow` spells out the instantiation procedure in its scaffold step | Skill stays small | Odin doctrine would carry method (header pre-fill, shape classification, attribution mechanics) — contrary to the repo's doctrine/method split; the license mechanics would live in an `odin-*` file | − | 0 | 0 | + |
| C. Rename to `brokk-arc42-template`; the skill's Purpose/When to Use/Workflow are rewritten as **Brokk's scaffolding procedure** (detect shape and next ADR, pre-fill header, write skeleton with guidance + attribution, mode-driven appendix treatment, report I-5); § Skeleton stays its payload; Odin's step 3 names the skill, the I-5 brief, and the Workfile; Kvasir's skill gains the fill-in rules and loses the template load | Skeleton + instantiation + shape detection in one Brokk-owned skill; Kvasir's skill is pure judgment; the fill rules Kvasir needs are short and travel with Kvasir | New dispatch + standing review per run; two rename-forced edits | + | − | + | 0 |
| D. As C, but Brokk also **prunes §1–§12 per the objective** | Kvasir receives fewer headings | Pruning is an architecture judgment ("include a section only when this objective affects it"); Brokk would decide scope it cannot justify, and the reviewer could not tell "Brokk pruned" from "Kvasir omitted" | 0 | − | − | 0 |
| E. Odin writes the scaffold itself, no Brokk dispatch | Cheapest | Odin produces no artifacts by its own boundaries; no owner for attribution/skeleton mechanics; no review of the skeleton | − | + | − | 0 |

## Decision
We use **C**, with pruning kept out of the scaffold (rejecting D). `brokk-arc42-template` (renamed and relocated by WP-0 with its two rename-forced edits; rewritten by WP-3) owns the § Skeleton **and** the scaffolding Workflow in §5.1.11: it reads the I-5 brief, classifies the target (arc42 directory / legacy single file / non-arc42 / none — the persistence skill's four shapes), resolves the next ADR number, writes the Workfile with a pre-filled header (`Status: Proposed`, `Date`, `Document scope`, `Mode … (source …)`, `Section scope: pending`, `Existing document` iff update delta), the attribution notice, all twelve headings with guidance intact, and mode-driven appendix treatment, fills **no** content and prunes **no** section, then reports the `Scaffold result` line. `odin-architecture-workflow` gains **step 3 — scaffold (always, both modes, both paths)**, between the context gate and drafting; its standing review is `heimdall-architecture-review` `Focus: scaffold` (ADR-0010 extension). `kvasir-software-architecture` loses lines 12 and 145's template load, gains a `Scaffold:` input and a short "Filling the scaffold" rule set (fill or mark every heading; delete guidance as you fill; delete the attribution notice iff no guidance survives), and its step 1 look-up shrinks to reading the pre-filled header and the existing document's sections. The template's rejected-because-Check-5 line 43 wording becomes "the architecture-drafting step". Brokk's persistence skill is unchanged.

**Why the skill needs explicit scaffolding behavior (not pure reference):** the repo's convention is that Odin doctrine "names the skill, the inputs, and the Workfile — never the method"; the instantiation mechanics (shape classification, header pre-fill, attribution placement) *are* method, so they belong in the skill the Brokk session loads. That also puts the CC BY-SA handling in the file that carries the licensed text.

## Consequences
- **Positive:** Kvasir's skill is judgment-only and no longer touches the repository to find document shape; skeleton, instantiation, and persistence share one owner (Brokk) and one shape vocabulary; the `Mode`/`Document scope`/`Existing document` header lines are set mechanically before drafting, so `Focus: document` can treat them as ground truth; the template moves to the Implementer inventory automatically (C-11).
- **Negative:** **+1 Brokk dispatch and +1 standing Heimdall review on every invocation, standalone and delegated** — Q-3 rises from ≤ 5 to ≤ 7 (≤ 9 with context), Q-5 records Δ = +2 for the engineering path, and NF-3 is superseded (R-12); the template's rename forces two content edits inside the scaffold package; the fill-in rules now exist in Kvasir's skill instead of the template (they are Kvasir's rules, so this is the right home, but the template's Workflow section must be rewritten, not merely trimmed).
- **Becomes harder:** running Kvasir's skill outside this workflow without a scaffolded Workfile — it now expects one; a caller that lacks it must dispatch the scaffold step first.
