# ADR-0022: A commit is a reviewed green tree state — batch boundaries, four commit types, and three branch prefixes fixed by the plan and the commit skill

- **Status:** Accepted
- **Date:** 2026-09-24
- **Kind:** recorded (evidence: `skills/engineering/kvasir-tdd-planning/SKILL.md:26-30, 75-97, 142-145, 153-156`; `skills/engineering/brokk-tdd-commit/SKILL.md:24-41, 63-66, 75-79`; `skills/engineering/heimdall-tdd-review/SKILL.md:120-125`; `skills/engineering/odin-tdd-workflow/SKILL.md:53, 56, 60, 83, 86-88, 98-99`)

## Context

Once history is written only after review (ADR-0020), what a commit *is* had to be fixed so that a suite run can prove it: a suite cannot test a staged subset of a dirty tree, wave packages coexist uncommitted in one tree, a second package's diff on a file the first also touched has no git reference until the first is committed, and a `Phase: red` result is by construction not green. The inline form had committed per phase, so a red commit was possible and the four commit types were mapped from phases rather than from packages. Branch conventions existed only in an optional skill bundle. Goals affected: system goal 1 (green means verified), goal 4 (a commit is traceable to exactly one reviewed batch), subsystem Consistency (one type mapping, one branch rule, stated once).

## Decision

**Every batch boundary is a verifiable green tree state**, fixed on the planning side by five rules (`kvasir-tdd-planning/SKILL.md:88-92`): the commit session's suite run proves the commit only if the tree beyond the staged set holds nothing but the recorded baseline-dirty paths; a parallel wave plus its integration is exactly one batch; consecutive sequential packages share a batch only if their write sets are pairwise disjoint — an intersecting write set starts a new batch so the predecessor is committed first; a scaffold is its own batch, committed before fan-out; no `Phase: red` result is a batch boundary — in split-phase mode the batch closes after the `green+refactor` review. Baseline-dirty paths are recorded path by path and never part of any batch; the commit count is minimal — one batch unless a rule forces a split or the user asked for small steps (`:96-97`). On the checking side the commit session verifies the tree equals the reviewed union plus baseline-dirty paths and runs the full suite after staging — green, or red on exactly the plan's baseline failures — or commits nothing (`brokk-tdd-commit/SKILL.md:63, 66`); the commit review re-runs the suite at `HEAD` and accepts only baseline-dirty leftovers (`heimdall-tdd-review/SKILL.md:124-125`). The orchestration applies the interleaving rule and commits the scaffold before fan-out (`odin-tdd-workflow/SKILL.md:53, 60`).

**Four commit types, mapped from package kind, normative in the commit skill alone** (`brokk-tdd-commit/SKILL.md:24-37`): feature → `feat:`; fix → `fix:` (reproduction test plus the fix); refactor → `refactor:` (behavior-preserving, with characterization tests); test → `test:` (tests only, green — "never a failing test"); scaffold → `feat:`, or `test:` when it adds only fixtures and declarations; a mixed batch → the kind of the package that delivers behavior, `feat:` > `fix:` > `refactor:` > `test:`. "Every commit is a reviewed green state, so the red, green, and refactor phases never produce separate commits" (`:26`). Subject grammar: `<type>: <imperative, lowercase subject, ≤ ~50 characters, no trailing period>`; a body only when the plan row supplies one (`:37`). The planner echoes the mapping and says the echo is not normative (`kvasir-tdd-planning/SKILL.md:93`); the commit session checks the row's type against the diff's shape and reports a mismatch rather than re-typing (`brokk-tdd-commit/SKILL.md:65`).

**Three branch prefixes, fixed in the commit skill** (`brokk-tdd-commit/SKILL.md:39-41`): a commit lands only on a branch prefixed `feature/`, `fix/`, or `refactor/`; the plan row says `current` when the branch conforms, else `create <type>/<kebab>` from the current branch with the prefix matching the dominant type (`kvasir-tdd-planning/SKILL.md:95`); the commit session creates it with `git switch -c` before staging, and stops when `current` does not conform or the name to create exists; "Never commit to `main`, `master`, `develop`, or any unprefixed branch, whatever the brief says." The commit review checks the branch name and prefix (`heimdall-tdd-review/SKILL.md:121`).

## Consequences

- **Positive:** every commit in a branch the framework wrote is a state in which the full suite passed, proven twice (committer, reviewer); a commit maps to exactly one plan row and one set of gating reviews, so `git log` on the branch reads as the commit plan; the type and branch conventions exist in one normative place each and the planner's echo is marked as such; `main` is unreachable from any session whatever the brief says.
- **Negative:** commits are coarser than in the inline form — a wave lands as one commit, a red phase never lands at all, so bisecting inside a batch is not possible; the rules couple three skills' grammars with no validator between them (§11 R24); a repository whose convention is unprefixed branches or other types cannot use the workflow without changing the commit skill.
- **Becomes harder:** committing a `Phase: red` result "to capture the tests", splitting a wave across commits, or batching two packages that touched the same file — each is a named anti-pattern (`kvasir-tdd-planning/SKILL.md:153-154`; `odin-tdd-workflow/SKILL.md:98-99`); a per-project branch or type convention — the set is closed in the skill.
