# ADR-0009: Image model selected by the OpenCode-native `model:` agent field, with install-site override in `opencode.json`

- **Status:** Accepted
- **Date:** 2026-09-20

## Context

Eitri must run on an image-capable model that teams can swap without code changes (C14; revision goal **Configurability**, rank 2). No Yggdrasil agent has ever carried a model selector — every agent carries only `temperature:` and runs on the OpenCode session default (context Workfile § Model Configuration; repo-wide search for `model:` returns nothing). The requirements name two candidate homes, "agent definition or `custom-capabilities.yaml`" (AC-7, AC-8), but `custom-capabilities.yaml` is an inventory input: `config-home/generate-capabilities.sh:272-321` reads `name`, `role`, `summary` and renders text, and nothing at runtime consumes the file — it can document a granted capability, not select a model. Two further forces: generated agent files are byte-validated (C4), so any repository-side default must live in the template head; and `setup.sh` overwrites same-named installed agent files on upgrade (`README.md:111`), so an override that lives in the installed `eitri.md` does not survive an upgrade. **Consistency** (rank 1) asks that the mechanism be a standard frontmatter key the existing toolchain already tolerates; **Maintainability** (rank 4) asks that it add no script logic; **Clarity** (rank 3) asks that the override path be one documented sentence.

- **Open question:** whether OpenCode honors a `model:` key in agent Markdown frontmatter and an `agent.<name>.model` key in `opencode.json`, and whether it accepts an image-capable model there. Not verifiable from this repository; the OpenCode agent-configuration documentation must be checked at ratification (R10).

## Options Considered

| Option | Pros | Cons | Consistency | Configurability | Clarity | Maintainability |
| --- | --- | --- | --- | --- | --- | --- |
| **A. `model:` frontmatter key in `eitri.template.md`; durable override via `opencode.json` `agent.eitri.model`; volatile override via the installed `eitri.md`** | Host-native; one line in the template; standard key the validator and capability generator already ignore; override survives upgrades; effective on next session | Depends on OpenCode honoring the key (open question); introduces a key no peer agent has; the override lives outside anything Yggdrasil validates (R16) | High — a frontmatter key like `temperature` | High — two override paths, one durable, zero repo edits | High — "set `agent.eitri.model`" is one sentence | High — no script change |
| **B. Tool-borne model: no `model:` field; the image model is whatever the post-install image tool (MCP) is configured with in the host's `mcp` config** | No new frontmatter key; model lives with the tool that uses it | Ties model configuration to a tool the requirements declare out of scope; nothing in the agent definition names the model (fails AC-7 as written); Eitri's own reasoning model stays the default, so a multimodal image-capable model cannot be used directly; out of the box there is no model to configure at all | Medium — no new key, but the agent says nothing about its model | Low until a tool exists; then Medium | Low — the "model" is hidden in MCP config | Medium |

Prompt-level config file: Eitri's Workflow reads `$CONFIG_BASE/yggdrasil/eitri.yaml` (`model:` key) and passes the value to whatever generates the image** | Framework-owned file, could be seeded by `setup.sh` like `custom-capabilities.yaml` | Requires `read` outside the project; prose-enforced, so model compliance decides whether it is honored (R4 class); invents a mechanism the host already provides; adds installer logic | Low — a bespoke mechanism | Medium — file-based, but only if the prompt obeys | Low — a second config file to learn | Low — new installer and prompt logic |

## Decision

We use **Option A**. Eitri's template head (`scripts/subagent-generator/eitri.template.md`) carries `model: <provider/model-id>` naming an image-capable model — the shipped default value is ratified separately (Appendix A item 2) — and every other agent stays without the key. An install-site operator changes the model by setting `agent.eitri.model` in the OpenCode configuration home's `opencode.json`, which `setup.sh` never writes, so the value survives every upgrade. The change takes effect on the next Eitri session — the next dispatch — with no repository edit, no regeneration, and no Yggdrasil-owned process to restart (NFR 6). *(Original text also offered a "volatile" second path — editing `model:` in the installed `eitri.md`; that path is withdrawn by the amendment below.)* `custom-capabilities.yaml` keeps its existing role: when a raster image tool is granted post-install, the operator documents it there with `role: designer` so planning sees it (`README.md:310-340`).

Rationale: A is the only option that satisfies **Configurability** with zero code and survives upgrades, and it is the most **Consistent** — a frontmatter key, parsed by nothing Yggdrasil owns, validated by Check 1 only for presence of `name`/`description`, and byte-compared by Check 4 like any other line. B fails the acceptance criterion's letter (the definition names no model) and leaves Eitri without any image-capable path until a tool is written; C re-implements what the host provides and rests on prose compliance; D cannot select anything.

**Amendment — 2026-09-21, post-implementation, user-directed (commit `e166fe5` on `feature/designer`; user confirmation: "Keep all of it as is.").** The in-repository half of Option A is withdrawn. `scripts/subagent-generator/eitri.template.md` and the generated `agents/eitri.md` ship with **no `model:` key at all** — neither a placeholder value nor the explanatory warning comment that accompanied it (13 lines removed; live frontmatter spot-checked at `eitri.template.md:1-25`: `name`, `description`, `mode`, `temperature`, `permission` only). Model configuration for Eitri therefore happens **entirely at the install site**, through the OpenCode configuration home's `opencode.json` key `agent.eitri.model`, with no in-repository trace, default, or discoverable signal that a model must be set. Absent that override, Eitri runs on the session default model like every other agent. The `opencode.json` override, its durability across `setup.sh` upgrades, and the manifest's `Model` row are unchanged and remain the whole mechanism.

**Amendment — 2026-09-21, reconciliation with the README (commit `fd0101a`, `README.md:357`).** The `agent.eitri.model` key in the configuration home's `opencode.json` is the **one ratified mechanism**. Hand-adding a `model:` key to the installed `$CONFIG_BASE/agents/yggdrasil/eitri.md` is **explicitly not a supported route** and is not ratified by this record, for three reasons the README states and this record adopts: no shipped agent carries the key, so whether the operator's OpenCode version honors a hand-added `model:` in Markdown frontmatter is unverified (R10); the next `setup.sh` run overwrites the installed file and reverts the edit (`README.md:111` merge semantics — same-named Yggdrasil files overwritten); and, after the first amendment, there is no shipped key to edit — the operator would be inventing one. Consequently R10's scope is exactly the `opencode.json` path: confirm at first install that OpenCode honors `agent.<name>.model` there; there is no fallback route this record endorses. Eitri is no longer the one agent carrying `model:` — no agent does — which restores full frontmatter parity with the five peers (**Consistency**) at the cost of the **Configurability** goal's "declared in the agent definition" half (AC-7's letter is now met only by the override path, not by the definition). This amendment is recorded as ratified by explicit user decision, not proposed.

## Consequences

- **Positive:** one README subsection delivers the whole mechanism; the operator's override is invisible to the repository and to `setup.sh`, so it can never be clobbered by an upgrade; the effective model is visible per run in the manifest's `Model` row, which makes a missing or ignored override observable after the fact (QS-12). *(Amended)* frontmatter parity with all five peers is preserved — no agent carries `model:`; R10 (host support for `model:` in Markdown frontmatter) is moot for the shipped files and narrows to the `opencode.json` path alone. *(Reconciled with `fd0101a`)* there is exactly **one** documented route, so operator instructions, this record, and the README cannot drift apart over a second path.
- **Negative:** correctness depends on host behavior the repository cannot test — QS-12/QS-14 are manual acceptance scenarios, not CI. *(Amended)* **Silent misconfiguration is now the default state**: a fresh install has no in-repo default, no comment, and no validator signal that Eitri needs an image-capable model; an operator who never sets `agent.eitri.model` gets a Designer running on the session default model, discovering it only when a manifest reports `unknown` or the wrong id, or when a brief for an image yields a blocked or degraded result. This is an **accepted, user-ratified trade-off** (R21); the README subsection WP-4 wrote is the sole discoverable instruction.
- **Becomes harder:** knowing from the repository alone what model Eitri runs on — the answer now lives only in each install's `opencode.json`; onboarding a new install site requires reading the README subsection rather than the agent file. *(Reconciled with `fd0101a`)* a quick local experiment — "just add `model:` to the installed file and try" — is not an endorsed way to test a model, so an operator without write access to `opencode.json` has no supported route at all. A future decision to give *every* agent a `model:` field must revisit the roster lists and Check 1 expectations together.
- **Risks and mitigations:** R10 (support unverified) → narrowed to `agent.eitri.model` in `opencode.json`, the only ratified route; confirm against OpenCode documentation at first install; a hand-added `model:` in the installed file is *not* a fallback (unverified, reverted by `setup.sh`, no shipped key). R16 (override outside validation) → the README names the exact key path and the manifest exposes the effective model. R21 (no in-repo signal) → accepted by the user; mitigation is documentation only — `README.md:341-357`.
