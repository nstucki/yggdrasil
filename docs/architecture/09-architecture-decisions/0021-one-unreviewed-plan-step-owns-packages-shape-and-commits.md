# ADR-0021: One unreviewed plan step owns the packages, the execution shape, and the commit plan

- **Status:** Accepted
- **Date:** 2026-09-24
- **Kind:** recorded (evidence: `skills/tdd/kvasir-tdd-planning/SKILL.md:3, 10-40, 42-84, 99-106, 123-133`; `skills/tdd/odin-tdd-workflow/SKILL.md:12-14, 39-45, 81-83, 101-102, 104`; `skills/engineering/odin-engineering-workflow/SKILL.md:24, 78`; `agents/kvasir.md:26-33`; `agents/odin-interactive.md:298`; `agents/odin-autonomous.md:302`)

## Context

The inline form left three decisions to the orchestration doctrine or to no one: whether the work could run as a parallel wave (five criteria the doctrine listed and Odin applied), which packages ran in which order (Appendix B as delivered), and how the work landed in history (each session committed as it finished). Deciding whether two write sets truly intersect, whether a contract is fixed, or whether a package is testable alone requires reading the packages against the codebase — specialist judgment the doctrine forbids Odin to perform (ADR-0001) — and a commit plan did not exist as an artifact at all. The Architecture workflow's drafting step had already established a shape for a Kvasir step whose Workfile is the contract every later session executes and that receives no review of its own (ADR-0016). Goals affected: system goal 2 (Odin orchestrates, a strategist plans), subsystem Maintainability (one grammar owner per hand-off), Consistency (the plan step has the drafting step's standing).

## Decision

The TDD workflow has **one plan step**, a Kvasir session with `kvasir-tdd-planning`, that answers three questions in one pass — how the work splits, how it executes, how it lands in history (`kvasir-tdd-planning/SKILL.md:10`) — and produces one plan Workfile with a fixed shape: header (`Branch:`, `Tree at planning:`, `Test command:`, `Baseline:`, `Packages from:`), `## 1. Packages`, `## 2. Execution Shape`, `## 3. Commit Plan`, `## 4. Risks and Gaps` (`:42-66`). **Packages are Appendix B verbatim** when an architecture Workfile exists — a defect in it is a report that the architecture is wrong, never a plan-side fix — or **exactly one derived package** when none does; a second package without an architecture Workfile stops the run with `packages=needs-architecture` and returns to the enclosing plan, whose shape verdict was wrong (`:24-25, 102`; `odin-tdd-workflow/SKILL.md:41, 102`). **The five parallel criteria live in this skill, once, as judgment against the live tree** — resolve the write sets, confirm each contract exists, confirm each package's tests run alone, confirm shared-surface churn sits in a scaffold, cap the wave at four (`:103`); the orchestration doctrine only records the resulting `Package check:` line and proceeds in parallel only when it reads all `yes` (`odin-tdd-workflow/SKILL.md:81, 83`). **The commit plan** is one table row per batch — packages, type, subject, body, gate — under the § Commit Plan Rules (`:75-97`; ADR-0022).

The planner resolves **exactly two repository facts** — `git branch --show-current` and `git status --porcelain`, both allowed to Kvasir by permission block (`:12`; `agents/kvasir.md:26-33`) — authors the Workfile, touches no project file, and **runs no tests**: the baseline is the context Workfile's or the brief's (`:14, 22-23`). Decisions are definite — "a plan the ratifier must finish is not a plan" (`:16`). **The step receives no review — permanently**: its gates are the plan checkpoint, where the user or adoption ratifies it, and the reviews of every session that executes it (`:18`; `odin-tdd-workflow/SKILL.md:14`); re-introducing a review of it "to be safe" is an anti-pattern (`:104`). The plan checkpoint always happens; whether it pauses is Communication-Policy-governed; a steered change is recorded as `Plan amended: <field>=<value> — <reason>` and carried in the briefs while the Workfile stays as drafted (`odin-tdd-workflow/SKILL.md:43-45`; `agents/odin-interactive.md:298`; `agents/odin-autonomous.md:302`). Two preconditions are reported, never guessed: no test-command source means the context skip was wrong and the context step fires; more than one package without an architecture Workfile stops the run (`odin-tdd-workflow/SKILL.md:41`; `kvasir-tdd-planning/SKILL.md:125-126`).

## Consequences

- **Positive:** Odin performs no specialist judgment inside the TDD workflow — the one rule it applies mechanically is the interleaving rule; the commit plan exists as a reviewable artifact before any code is written and is what the user steers at the checkpoint; the `Package check:` and `TDD plan:` grammars have one owner (§5.2 T-3); the plan step has the same standing as the drafting step, so the doctrine has one rule for unreviewed Kvasir steps in packaged workflows (§8.1).
- **Negative:** a mis-batched or mis-shaped plan is caught only downstream — by the commit session's tree check, the commit review, or a package review's write-set breach — never by a review of the plan (§11 R3); the planner cannot verify its baseline and depends on the context step or the brief for it.
- **Becomes harder:** re-deriving or "improving" an Appendix B package inside the TDD workflow — the checkpoint is the only place a plan changes, and the architecture stage is where a package split changes (`odin-tdd-workflow/SKILL.md:101`; `kvasir-tdd-planning/SKILL.md:150`); running the TDD workflow on a multi-package objective without an architecture document.
