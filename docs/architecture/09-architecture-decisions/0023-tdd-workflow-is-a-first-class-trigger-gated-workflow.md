# ADR-0023: The TDD workflow is a first-class trigger-gated workflow — its own command and check, split from the Engineering check by intent, with a standalone safety stop

- **Status:** Accepted
- **Date:** 2026-09-29
- **Kind:** recorded (evidence: `commands/yggdrasil/tdd.md:1-13`; `agents/odin-autonomous.md:211-229, 306, 311-313` and the same sections of `agents/odin-guided.md`, `agents/odin-interactive.md:302, 307-308`; `scripts/odin-generator/shared-body.template.md:184-202`; `scripts/odin-generator/communication-policy-{autonomous,guided,interactive}.fragment.md` (`TDD suggestion candidate`, `TDD plan checkpoint` bullets; the Interactive `Commands` bullet); `skills/tdd/odin-tdd-workflow/SKILL.md:3, 10, 26-34, 44, 65, 95, 105`; `skills/engineering/odin-engineering-workflow/SKILL.md:3, 24, 26, 30-31, 43, 51`; `skills/tdd/kvasir-tdd-planning/SKILL.md:25, 102, 126`; `setup.sh:167, 174, 361-372`; `scripts/validate.sh:767`; `README.md:72, 133, 236-237, 412-428, 443-446`)

## Context

ADR-0019 recorded the TDD workflow as a standalone doctrine skill that composed as a stage of the Software Engineering workflow and had "no trigger verdict of its own", being "standalone *by design*, so an entry point can be added later without touching it". The consequence was that a bounded, test-first change — a bug with a reproduction, a feature with stated behavior, a refactor wanting characterization tests — could reach the reviewed-commit path only through the Engineering check, whose shape verdict, optional analysis, and optional architecture stage exist for requests that need requirements pinned down or a design decided. The Engineering check's own trigger rule named test-driven-development language as an invoke, so the heaviest packaged workflow was the only door to the lightest reviewed implementation, and the six TDD skills lived under `skills/engineering/` beside the skill that ran them. Goals affected: system goal 5 (extensibility at the install site — a reviewed test-first change should cost no more ceremony than it needs), subsystem Consistency (every packaged workflow has a trigger of its own; exactly one check owns any request), subsystem Maintainability (one workflow body serves both entry paths — the stage-composition rule of ADR-0019 is kept, not replaced).

## Decision

The TDD workflow is a **first-class trigger-gated packaged workflow**. It has its own command, `/yggdrasil/tdd <objective>`, whose file follows the command definition contract and directs the Interactive Odin to load `odin-tdd-workflow` (`commands/yggdrasil/tdd.md:1-13`; §5.1.4). It has its own section in Odin's shared body — description, `TDD check: command=<yes/no>, explicit-request=<yes/no> → <invoke/skip/suggest>`, invariant trigger rules, and the `On invoke` load directive — generated into all three modes, and its own two Trigger-Threshold bullets in every Communication Policy fragment: the `TDD suggestion candidate` (skip in Autonomous, suggest in Guided and Interactive) and the `TDD plan checkpoint` (auto-proceed in Autonomous and Guided, pause in Interactive), the latter replacing the former "Software Engineering — TDD stage plan checkpoint" bullet (`agents/odin-autonomous.md:211-219, 311-312`; `agents/odin-interactive.md:302, 307-308`; `shared-body.template.md:184-192`). Its six skills live under `skills/tdd/`, a mandatory feature directory of the installer and the validator, and their former `engineering/` paths are purged at every upgrade (`setup.sh:167, 174, 361-372`; `scripts/validate.sh:767`).

**The TDD and Engineering checks partition one request space by two symmetric rules, each stated in both trigger sections.** By intent: explicit test-driven-development, test-first, or red-green-refactor language *without* requirements-analysis or architecture-before-implementation intent → `TDD check: invoke`, and the Engineering check reads "*without* it → skip here; the TDD check owns it"; the same language *with* such intent — "requirements to pin down, a design to decide, or a change that introduces structure or splits into two or more work packages" — → `Engineering check: invoke`, and the TDD check reads "skip here; the Engineering check owns it and runs this workflow as its implementation stage" (`agents/odin-autonomous.md:217, 227`). By shape, for the suggestion candidates: "a bounded implementation request that fits the existing structure in one package and states its behavior testably … without test-first language" is the TDD check's candidate and "the TDD check's candidate, not this one's" in the Engineering section; "a non-trivial implementation request that introduces structure or would split into two or more work packages" is the Engineering check's candidate and "the Engineering check's candidate, never this one's" in the TDD skill (`odin-tdd-workflow/SKILL.md:32-34`; `odin-engineering-workflow/SKILL.md:30-31`). A trivial change, a request for direct implementation, a research request, or a question is a skip for both.

**One body, two entry paths.** `odin-tdd-workflow` § When to Use names both entries — the `TDD check` verdict `invoke` and "as a stage of a larger plan … today from the Software Engineering workflow's TDD step" — and fixes that "the mechanics are identical either way, and only where the Response lands differs" (`:28-29`); the Response step is folded into the enclosing plan's when staged (`:65`) and adds one dispatch to the cost model when standalone (`:95`). The Software Engineering workflow's description, `Kvasir Consultation Check` text, and step 4 continue to run the TDD workflow to completion as a stage, unchanged in form (`odin-engineering-workflow/SKILL.md:3, 24, 26, 51`); ADR-0019's composition rule stands.

**The standalone safety stop is the one path-dependent rule.** The plan step never derives more than one package without an architecture Workfile and reports `packages=needs-architecture` (`kvasir-tdd-planning/SKILL.md:25, 102, 126`). "As a stage of the Software Engineering workflow, its shape verdict was wrong and the Architecture stage must fire. **Standalone**, the run ends with a Response that names the route — the Software Engineering workflow (`/yggdrasil/engineer`), whose architecture stage makes the split this workflow does not — and nothing is left in the tree" (`odin-tdd-workflow/SKILL.md:44`); the anti-pattern list restates it — "return to the enclosing plan, or — standalone — end the run and name `/yggdrasil/engineer`" (`:105`). The stop precedes every implementation dispatch, so a standalone run that ends here has dispatched no Brokk session and changed no path in the working tree.

Rationale, against the ranked goals: system goal 5 — a reviewed test-first change is reachable by one command or one sentence, with no shape verdict and no analysis or architecture stage to decline; Consistency — the fifth packaged workflow now has the same three-part trigger shape as the other four (command, explicit language, suggestion candidate), and the intent rule appears in both checks so no request falls to both or to neither; Maintainability — the entry path is added around the body, as ADR-0019 anticipated, and the body reads the path in exactly one place. The alternative shape — a separate lightweight "TDD-lite" doctrine, or an Engineering shape verdict with `analysis=no, architecture=no` as the standalone form — was not adopted by the repository: the former would duplicate the plan, execution, and commit doctrine, the latter keeps the ceremony the split exists to remove.

## Consequences

- **Positive:** every packaged workflow is invocable on its own terms; a one-package test-first change is one command away and costs `T + 1` dispatches, minimum 6; the TDD and Engineering checks cannot both fire on one request because each states the other's ownership; the Engineering workflow is unchanged as an enclosing plan; the `tdd/` directory makes the family's boundary a listing check and the purge list keeps the old paths from staying loadable (§11 R23).
- **Negative:** intent is inferred by Odin from the request, and the two-or-more-packages boundary is knowable only after the plan step — a standalone run on a change that needs two packages pays up to four dispatches before the safety stop ends it and then asks the user to re-issue the request (§11 R27); Odin's shared body grew a trigger section, so every generated Odin agent and every line-number citation beyond it moved (§11 R26); ADR-0019's statement that the workflow has no trigger verdict is now false and its evidence citations into `odin-tdd-workflow` point at other text (§11 R18).
- **Becomes harder:** treating "the TDD stage" as a distinct thing from "the TDD workflow" — there is one body and the doctrine says so; adding a path-dependent rule anywhere other than the safety stop without breaking "the mechanics are identical either way"; promoting a standalone run into the Engineering shape mid-flight — the doctrine ends the run and names the route instead.
