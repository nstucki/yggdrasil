# ADR-0024: Two narrow writes to persisted files — a correction scope re-persists named topic documents, a superseding record flips the superseded record's status line, and nothing else in a record ever changes

- **Status:** Accepted
- **Date:** 2026-09-29
- **Kind:** recorded (evidence: `skills/architecture/brokk-architecture-persistence/SKILL.md:67, 98, 135, 137, 150, 154, 162, 165-167, 182, 186-187` (§ The Persisted Layout "Topic document"; § When to Use; § Workflow steps 5–7; § Quality Criteria; § Anti-Patterns); `skills/architecture/kvasir-software-architecture/SKILL.md:117-118, 180, 189, 220` (§ Layout Map rules 4–5; § Decision Record Format; § Output Contract item 2; § Quality Criteria); `skills/architecture/heimdall-architecture-review/SKILL.md:87-88, 92, 94, 96, 107, 125` (items (a), (b), (f), (h), BLOCKED; § Quality Criteria; § Anti-Patterns))

## Context

ADR-0014 made the topic document the unit of an update delta, and ADR-0017 made the persistence step the only writer of the layout, with the rule that it never deletes and never edits an existing record. Two gaps followed. A persisted topic document whose Workfile source was corrected after persistence could be fixed only by replaying the delta — colliding on record IDs and duplicating §9 and Change Log rows — or by hand, leaving its `Last updated`, its section index, and the top index behind; the persistence skill now names both as an anti-pattern (`brokk-architecture-persistence/SKILL.md:186`). And a superseded record gave its reader no on-page signal: ADR-0014 read `Status: Accepted` with no mention of ADR-0016 or ADR-0017, ADR-0018 the same relative to ADR-0019, ADR-0013 the same relative to ADR-0016, because the supersession lived only in the superseding record's `Related` and in §11 R18 — a reader who opened the old record without the log took a superseded clause for the current rule. Goals affected: subsystem Maintainability (a one-document fix is a one-document write; a supersession is a one-line write), Clarity (a reader learns a record is superseded from the record itself), Durability (the decision log stays append-only and a record's substance is never rewritten), Consistency (both writes are driven by the brief or the map and checked by the same mechanical review as a delta).

## Decision

**The persistence step has exactly two ways to change a file it already wrote, and each changes one thing.**

*Correction scope* re-persists named **topic documents**. It is entered only when the brief carries `Re-persist: <path>[, <path> …] — <reason>` — a grammar "fixed here and nowhere else" — and the header's `Document scope:` is not applied (`brokk-architecture-persistence/SKILL.md:98, 137`). Preconditions replace the delta's: the target is the folder layout by the identity rule; every named path exists in it and is a topic document — "a path under the record directory is refused (`precondition failed — record correction: <path>`; a record's body is corrected only by a superseding record in a delta, and its status line only by that record's `→ status:` row in the same or a later delta — never in correction scope)"; Appendix A IDs already on disk are expected and `Records from:` is not checked; the `Ratification:` line is still validated and promotes nothing. Each named document is replaced whole-file from the Workfile heading Appendix C assigns it, at its existing ordinal, with the same promotion and backlink; each affected section's index and the top index's header and Sections table are regenerated so their `Last updated` is the run date; exactly one Change Log row with scope `correction` is appended; no record is written, no §9 row appended, and every other path stays byte-identical (`:137`). The manifest reads `scope=correction` with `replaced` per named path, and the quality criterion fixes the changed-path set as "exactly the `Re-persist:` paths, their section indices, and the top index" (`:168`); the review checks the existence rule at baseline with every `Re-persist:` path present, and map ⇔ tree with exactly those paths plus indices in the diff, no record and no §9 row, and a `correction` Change Log row (`heimdall-architecture-review/SKILL.md:87-88`).

*Status-line supersession* flips one line of an existing **record**, inside an update delta, on an Appendix C row `| ADR-NNNN (existing record) | → status: <status text> | — |`. The status text "is exactly one of `Superseded by ADR-MMMM[, ADR-MMMM …]` or `Accepted — superseded in part by ADR-MMMM[, ADR-MMMM …]` — this grammar is fixed here and nowhere else" (`brokk-architecture-persistence/SKILL.md:135`); the drafter chooses the first when the superseding record replaces the whole Decision and the second when any clause still stands, and echoes the grammar as "the persistence step's § Workflow step 5 owns the grammar and its preconditions — this is an echo" (`kvasir-software-architecture/SKILL.md:117`). Preconditions, all checked before any write: `ADR-NNNN` resolves to exactly one `NNNN-*.md` in the record directory and is not an Appendix A ID of this run; every `ADR-MMMM` is in `ratified=` or already on disk at `Status: Accepted`; each such record names `ADR-NNNN` under its `## Related` heading (in Appendix A when new, in its file when existing); the record's current status line is `- **Status:** Accepted` or a prior supersession form whose every ID the new text also carries — a `Proposed` record is refused; any failure is `precondition failed — status supersession: <which>` and nothing is written. The write is "**exactly the line beginning `- **Status:** `** in the record" and "**exactly the `Status` cell** of that record's row in `09-architecture-decisions/README.md`", every other byte of both files unchanged, `git diff --numstat` for the record reading `1 1` (`:135`); the §9 log is "append-only apart from a `→ status:` cell" (`:165`); the delta's changed-path set adds "the records named by `→ status:` rows" (`:167`); the manifest action is `status superseded` (`:150, 154`). The drafter never edits the superseded file — it names the supersession under the new record's `Related` (as `supersedes …`, stating which clauses or citations), adds the `→ status:` row, and states both on the decision-list line the checkpoint surfaces (`kvasir-software-architecture/SKILL.md:180, 189`). The review runs `git diff --numstat` on every `→ status:` record and requires `1 1` with the removed line `- **Status:** Accepted` or a prior form and the added line in one of the two forms, every named ID `Accepted` after the run and naming the superseded record under `Related`, prior IDs preserved, and the §9 row changed in its `Status` cell only; it then diffs **every** other pre-existing record and requires zero changes — any other change to a pre-existing record, a status text outside the two forms, or an ID that is `Proposed`, absent, or does not name the superseded record is blocking (`heimdall-architecture-review/SKILL.md:88, 92, 96, 107`).

**Everything else in a record is immutable by every path.** "A record's body is never rewritten, and its one mutable field is the `Status:` line, promoted at its own persistence and later flipped only by a `→ status:` row" (`brokk-architecture-persistence/SKILL.md:67`); title, Context, Decision, Options Considered, Consequences, Related, Date, and Kind are answered by a later record that names what it supersedes, and the status line is the pointer from the old record to that answer. The correction scope refuses record paths; the delta path writes new records and flips status lines; no path edits a body, and the persistence skill names "touching any line of an existing record other than its `Status:` line, or flipping a status no ratified record claims" as an anti-pattern (`:187`). The Layout Map's three-way accounting — re-authored, superseded, carried forward — is over **topic** documents; a status-flipped record is outside that walk and accounted for by its own row (`kvasir-software-architecture/SKILL.md:118`).

Rationale: Maintainability is the driver for both writes — one document plus its indices, or one line plus one cell, each verified by the same mechanical review as a delta. Clarity is the driver for the status line specifically: the supersession relationship already existed — in `Related`, in §9, in §11 R18 — but was invisible from the superseded record, which is where a reader lands. Durability is preserved by making the status line the *only* mutable field and making it monotonic — IDs are appended, never removed — so the log's append-only property and every record's substance stand; editing the superseded body to strike or annotate clauses was not adopted because it makes the historical record a moving target and every such edit a judgment the persistence step is designed not to have. Consistency holds because both writes are subsets of the delta's write — same promotion, same indices, same review items with one branch each — and the flip is gated on the same ratification that accepts the superseding record.

## Consequences

- **Positive:** a persisted topic document can be fixed without a delta, a new record, or duplicated log rows; a superseded record says so on its second line, in a form a reader and a grep both recognize; the flip is impossible without an `Accepted` record that claims the supersession under `Related`, so a status line can never point at nothing; the review's diff of every pre-existing record makes any other change to any record blocking — a stronger guarantee than the previous "never edit" prose alone.
- **Negative:** the persistence step carries three write paths and one exception in one skill; a correction still requires a corrected Workfile heading for Appendix C to assign; `Accepted — superseded in part by …` tells the reader *that* clauses fell, not *which* — the superseding record's `Related` still carries that; a record whose only superseded content is an evidence citation stays `Accepted` with stale line numbers inside it (§11 R26); the `Ratification:` line is required but inert on the correction path.
- **Becomes harder:** editing a record body by any workflow path — every path refuses it and the review diffs for it; "fixing" a document by hand and leaving the indices stale; flipping a status speculatively, before the superseding record is ratified, or for a record no `Related` claims.
