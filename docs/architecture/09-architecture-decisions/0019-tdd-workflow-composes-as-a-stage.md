# ADR-0019: The TDD workflow is standalone and composes as a stage of the Software Engineering workflow

- **Status:** Accepted — superseded in part by ADR-0023
- **Date:** 2026-09-24
- **Kind:** recorded (evidence: `skills/tdd/odin-tdd-workflow/SKILL.md:3, 10-31, 62`; `skills/engineering/odin-engineering-workflow/SKILL.md:3, 10-14, 24-26, 35-43, 47-53, 57-64, 71, 78`; `skills/tdd/mimir-tdd-context/SKILL.md:2-3, 6, 12, 37`; `skills/tdd/heimdall-tdd-review/SKILL.md:2-3, 6, 10-19`; `skills/architecture/odin-architecture-workflow/SKILL.md:37, 91`; `skills/architecture/heimdall-architecture-review/SKILL.md:44`; `agents/odin-autonomous.md:213, 302`; `scripts/odin-generator/shared-body.template.md:186`; `scripts/odin-generator/communication-policy-interactive.fragment.md:19`; `setup.sh:174, 361-366`; `README.md:72, 132, 411-423`)

## Context

The Software Engineering workflow carried test-driven implementation inline: after its optional analysis and architecture steps, the same doctrine skill dispatched the behavioral-context step, decided the parallel criteria, ran the work packages, integrated, and committed — five steps of one skill, with a `context=` field in the shape verdict that had to be amended after the architecture stage because the information deciding it did not yet exist when the verdict was recorded. The Architecture workflow had already been extracted from that same skill into a standalone, stage-composed form (ADR-0018), so the two halves of one workflow composed differently: one by staging, one inline. Goals affected: subsystem Consistency (every packaged workflow composes the same way), Maintainability (one doctrine skill per workflow; a change to the TDD steps changes no other skill), system goal 2 (the enclosing orchestration does no specialist work — the parallel criteria are judgment).

## Decision

The TDD workflow is a **standalone packaged workflow** carried by its own doctrine skill, `odin-tdd-workflow`, and composes **as a stage**: the Software Engineering workflow loads it and runs it to completion — context gate, plan, plan checkpoint, reviewed packages, integration, review-gated commits — exactly as it runs the Architecture workflow; "No request line and no result line exist" (`odin-tdd-workflow/SKILL.md:28`). The inner skill fixes its own Deliverable (`:20-22`), owns its own cost model `T = 2C + 1 + 2N·(1+S) + 2W + 2K` (`:92`), states its own Kvasir-Consultation exemption (`:24`), and folds its Response into the enclosing one when staged (`:62`). It has no trigger verdict of its own and is standalone *by design*, so an entry point can be added later without touching it (`:29`).

The enclosing skill is reduced to what is not a stage: a shape verdict over the two optional steps, `Engineering shape: analysis=<yes/no — reason>, architecture=<yes/no — reason>` — the `context=` field and its amendment clause are gone, because behavioral context is the TDD stage's own conditional gate (`odin-engineering-workflow/SKILL.md:38-43`; `odin-tdd-workflow/SKILL.md:35`) — business analysis, the Architecture stage, one TDD-stage step, and the Response (`odin-engineering-workflow/SKILL.md:35-55`). Its review table names no review of its own: "every review gate of this workflow runs inside its stages" (`:57-62`). Its cost model names both stages' counts as terms, `A + R·D + T + 2`, minimum 7 (`:71`). The enclosing run passes into the stage only the objective and the Workfiles it produced — passing packages, modes, batches, or commit instructions is an anti-pattern (`:78`).

The stage's method skills are named for the workflow they serve: the behavioral-context skill is `mimir-tdd-context` and the review skill is `heimdall-tdd-review` (`mimir-tdd-context/SKILL.md:2, 6`; `heimdall-tdd-review/SKILL.md:2, 6`), matching `mimir-architecture-context` / `heimdall-architecture-review`. The two context shapes are mutually non-substitutable: the Architecture workflow names a TDD-context Workfile never a skip reason, the TDD workflow names an architecture-context Workfile never one, and each review skill routes the other shape to its owner (`odin-architecture-workflow/SKILL.md:37, 91`; `odin-tdd-workflow/SKILL.md:35`; `heimdall-tdd-review/SKILL.md:19`; `heimdall-architecture-review/SKILL.md:44`). Odin's shared body and the three Communication Policy fragments state the composition and the TDD stage's plan checkpoint, generated into every Odin agent (`shared-body.template.md:186`; `communication-policy-interactive.fragment.md:19`; `agents/odin-autonomous.md:213, 302`). The installer purges the two pre-rename skill directories at the destination before copying (`setup.sh:174, 361-366`).

## Consequences

- **Positive:** two workflows compose by one rule (§8.5), so the Skill Library's provided interface for workflows stays uniform — trigger verdict or stage entry, an `odin-*` skill, a fixed `Deliverable:` line, a stated cost model; the enclosing skill shrank from an inline implementation doctrine to a shape verdict plus two stage steps, and the amendment machinery for `context=` disappeared with the field; the TDD workflow can gain a command or trigger later without a change to its body; the parallel criteria left the orchestration doctrine for the planner (ADR-0021).
- **Negative:** a medium run costs one to three dispatches more than the inline form — a real planning step and a reviewed commit (§4 item 13; §11 R22); the enclosing plan depends on what two stages "left in the conversation", so a stage whose report items are malformed is caught at the enclosing Response's Final Review Gate, not by a grammar check.
- **Becomes harder:** running part of the TDD workflow inside another plan — one package without a plan, or a commit without the plan row — is not a supported composition; the stage runs whole. Historical records ADR-0016 and ADR-0018 cite line ranges of `odin-engineering-workflow/SKILL.md` that this decision moved or removed (§11 R18).
