# ADR-0011: Designer as sixth role-bound specialist, registered by in-place extension of the roster lists (supersedes ADR-0001)

- **Status:** Accepted
- **Date:** 2026-09-20

## Context

ADR-0001 records "exactly one primary agent … and **five** subagents", with Odin's `task` allowlist "restricted to the five specialists by name" (`docs/architecture/09-architecture-decisions/0001-…md:13`). The user has fixed that Eitri is a sixth peer role (C12), so ADR-0001's count is superseded — the question this record decides is *how* the sixth specialist is registered. Registration in this framework is implicit: the agent file's `name:` is the dispatch key and Odin's `task:` block is the allowlist (context Workfile § Entry Points 1) — but the roster is also spelled out literally in seven script and template locations: `scripts/generate-subagents.sh:68, 74` (`SUBAGENTS`, `WORKFILE_AUTHORS`); `scripts/validate.sh:351, 450-451, 486, 520` (Checks 4, 5, 6); `config-home/generate-capabilities.sh:180-189, 256-269, 323-433` (role map, description loop, five render sections); `scripts/ci-smoke-subagent-generator.sh:40, 68-72`; `scripts/ci-smoke-generator.sh:105-109, 121`; `scripts/odin-generator/preamble.template.md:12-18`; plus prose lists in `scripts/README.md:37, 46, 57, 93` and `README.md:11, 91, 277, 287, 329, 486`. The requirements assumed the generator needs no logic change (`01-requirements.md` § Assumptions row 4); it does (R18). The capability inventory renders one section per role and its role vocabulary (`researcher|implementer|reviewer|strategist|communicator`) is the contract between `custom-capabilities.yaml`, the inventory, and Odin's Agent Selection Guide ("Role names match the inventory's sections", `shared-body.template.md:21`). Forces: **Consistency** (the sixth agent enters through the same doors as the five), **Maintainability** (a seventh must be addable by analogy), C2 (bash 3.2 `cat`/`sed` simplicity), and standing goal S3 (Check 4 byte-identity must keep holding across nine files).

## Options Considered

| Option | Pros | Cons | Consistency | Configurability | Clarity | Maintainability |
| --- | --- | --- | --- | --- | --- | --- |
| **A. Extend every roster list in place** — add `eitri` to each literal list, add a `designer` arm and a `### Designer` render section to the capability generator, add `eitri: allow` to Odin's preamble and one Agent Selection Guide row; document the touch list in `scripts/README.md` | Smallest diff; every script keeps its shape; no new file, no new abstraction; each list is next to the check that uses it; bash-3.2-safe | The roster stays duplicated in seven places (R12); a future omission in one list is caught by Check 4/5 for some lists but not for the capability generator's | High — exactly how the five are registered today | n/a | High — the change is visible where it takes effect | Medium — by analogy, with an enumerated list; not by single source |
| **B. Introduce a single roster manifest** (e.g., `scripts/roster.txt` or derivation from `scripts/subagent-generator/*.template.md`) consumed by generator, validator, smoke tests, and the install-side capability generator | One place to add a specialist; eliminates R12 | The install-side capability generator runs against the installed layout, not the repository, so it cannot read a repo manifest — it would need the roster shipped to the config home, a new install artifact; validator must stay read-only and portable; refactors four scripts and the render section (the six role sections are literal heredocs) far beyond this objective; changes the failure modes Check 4/5 rely on | Medium — a new mechanism no existing agent used | n/a | Medium — indirection | High long-term, but at a cost this objective does not carry |
| **C. Register Eitri under an existing role** (e.g., as a second `implementer`) to avoid a sixth inventory section | No capability-generator change | Violates C12 (sixth *peer role*); the inventory would route image work to "Implementer"; the Agent Selection Guide would misname the role | Low | n/a | Low | Medium |

## Decision

We use **Option A**. Eitri is registered by adding `eitri` to every literal roster list, in alphabetical position where the list is alphabetical (`bragi brokk eitri heimdall kvasir mimir`) and in place elsewhere; `eitri` joins `WORKFILE_AUTHORS`; the capability generator gains the arm `eitri) role="designer"`, a `designer_skills` accumulator, `eitri → designer_desc` in the description loop, and a `### Designer` section rendered after `### Communicator`; `config-home/custom-capabilities.yaml:15` and `README.md:329` list `designer` in the role enum; Odin's preamble gains `eitri: allow` and the shared body gains one Agent Selection Guide row plus the roster-shaped sentence edits at lines 49, 45, 150, and 225; `scripts/README.md` gains a subsection enumerating every roster location a future specialist must touch. ADR-0001 is **superseded** in its count by this record: the system has exactly one primary agent and **six** subagents; every other clause of ADR-0001 — Odin alone holds `task`, specialists cannot task one another, Odin never performs specialist work, validator Check 5 enforces isolation — remains in force unchanged. Option B is recorded as debt R12 for a future revision.

Rationale: A is the **Consistent** path — the five were registered exactly this way — and it is the only option that stays inside the objective's scope and C2's simplicity; B is the right long-term answer to R12 but is a toolchain refactor with an install-side artifact of its own, not a precondition for adding one agent; C violates a ratified constraint.

## Consequences

- **Positive:** every check that guards the five now guards six with no new mechanism; the `designer` role slug becomes usable in `custom-capabilities.yaml` immediately, so a post-install image tool can be documented against the right role; the Agent Selection Guide and the inventory agree on six role names.
- **Negative:** seven roster edits in one commit, with the capability generator's omissions not caught by the repository validator (R7/R12); the inventory's Designer section reads `(none)` until an `eitri-*` skill ships (Appendix A item 7).
- **Becomes harder:** nothing structurally — but the cost of the next specialist is the same seven edits, and R12 grows with each one.
- **Review-rule consequence (ADR-0002 applied):** Eitri writes Artifacts, so every Eitri session receives a dedicated Heimdall review and Eitri joins the "every Mimir/Brokk dispatch" clauses at `shared-body.template.md:150, 225`; the Check 7 marker `receives a dedicated Heimdall review` is preserved verbatim.
- **Risks and mitigations:** R12 → enumerated touch list in `scripts/README.md`, QS-17. R18 → reported to the requesting agent as a requirements-assumption correction. Partial-edit risk → Check 4 fails if `SUBAGENTS` gains `eitri` without the template or vice versa; Check 5 fails to scan `eitri.md` if `SUBAGENT_NAMES` is not updated, which QS-9's "10 of 10" only proves indirectly — WP-1's red test asserts the four validator lists contain `eitri`.
