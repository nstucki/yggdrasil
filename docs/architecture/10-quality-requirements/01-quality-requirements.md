## 10.1 Quality Requirements Overview

The quality tree refines the goals of §1.2 into the attributes the system's mechanisms observably serve. Rows 1–5 refine the five inferred system goals; rows D1–D5 refine the five stated goals of the architecture-documentation subsystem. Every leaf traces to a mechanism cited in §5 or §8.

| Goal (§1.2) | Attribute | Mechanism |
| --- | --- | --- |
| 1 Independent verification | Reviewer independence; ground-truth verification; gate completeness; history gated by review | §8.1 review gates; §8.10 review-gated history; `agents/odin-autonomous.md:255-275`; §5.2 T-1 |
| 2 Role isolation / least privilege | Tool-surface minimality; cross-agent opacity; scope discipline; judgment and mechanics in separate sessions | §8.2, §8.6; permission blocks; validator Check 5; §5.2 T-4 |
| 3 Reproducibility | Generator determinism; committed-vs-generated parity | §8.8; validator Check 4; smoke tests |
| 4 Traceability | Source citation; counts proven by enumeration with unit and method; Memory provenance and lifecycle; committed path set = reviewed union | §8.4; §5.1.3 research proof contract; Memory schema `sources`, `confidence`, `status`; §8.10; §5.2 T-1 |
| 5 Extensibility at install site | Repo-untouched extension; inventory regeneration; a bounded test-first change reachable without the Engineering shape | §5.1.8; `custom-capabilities.yaml`; `generate-capabilities.sh`; §5.1.4 `/yggdrasil/tdd`; §8.5 trigger split |
| D1 Durability | Task-scoped content excluded at source and at drafting; its pattern-matchable subset blocked at persistence; references resolve inside the document; the decision log is append-only even under correction | §5.2 I-1, I-3, I-4, I-5 correction scope |
| D2 Clarity | Omission reason visible in the marker; scope stated in the header line and the report; a superseded record names its superseding record(s) on its own `Status:` line | §5.2 I-2; §5.2 I-5 status-line supersession |
| D3 Maintainability | Delta touches only the documents the objective changes; a correction touches only the named documents and their indices; a supersession touches one record line and one §9 cell; refresh on re-authoring; header ⇔ tree verified before writing; one grammar owner per hand-off; one workflow body serving two entry paths | §5.2 I-1 refresh rule, I-5, I-7; §5.2 T-3, T-7 |
| D4 Consistency | One test text, one workflow form, zero scope exemptions; two workflows compose by the same staging rule; every packaged workflow has a trigger of its own and exactly one check owns any request | §5.2 I-1; §8.5 staging and trigger partition; §5.2 T-5, T-7 |
| D5 Usability | §5 and §9 carry contracts and decisions, no implementation-phase guidance | §5.2 I-1 per-section application |
