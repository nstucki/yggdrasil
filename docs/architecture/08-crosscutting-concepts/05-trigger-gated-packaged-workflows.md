# 8.5 Trigger-Gated Packaged Workflows

_Part of [Yggdrasil — Architecture (arc42)](../README.md) · [§8](README.md)._

Five workflows — Deliberation Council, Research, Architecture, TDD, Software Engineering — are invoked whole rather than composed. Each has invariant trigger rules in Odin's shared body (command → invoke; explicit language → invoke; a named suggestion candidate → per Communication Policy; factual, trivial, or executable request → skip), a one-line triggering verdict, and a dedicated `odin-*` skill that Odin loads on `invoke` and that carries the full mechanism, constraints, cost model, and the workflow-fixed `Deliverable:` line (`agents/odin-autonomous.md:172-229`, § Workflows; `skills/architecture/odin-architecture-workflow/SKILL.md:10-24`; `skills/tdd/odin-tdd-workflow/SKILL.md:10-24`). Standing rules: every workflow ends at the Final Review Gate; the Kvasir Consultation Check records `skip — packaged workflow`; a workflow nested in a composite plan does not exempt the composite (`agents/odin-autonomous.md:176-179`). Each workflow's suggestion-candidate handling and checkpoint pause behavior are completed by the mode's Trigger Thresholds, the TDD workflow's `TDD suggestion candidate` and `TDD plan checkpoint` among them (`agents/odin-autonomous.md:302-313`).

**Trigger ownership is partitioned by intent.** Where two workflows could claim one request, the shared body states the split symmetrically in both trigger sections so that exactly one check invokes. Architecture language *with* implementation intent is the Engineering check's, *without* it the Architecture check's (`agents/odin-autonomous.md:207`). Test-driven-development, test-first, or red-green-refactor language *without* requirements-analysis or architecture-before-implementation intent is the TDD check's; the same language *with* that intent — requirements to pin down, a design to decide, a change that introduces structure or splits into two or more work packages — is the Engineering check's, which runs the TDD workflow as its implementation stage. The suggestion candidates are partitioned the same way: a bounded, testably-stated change that fits the existing structure in one package is the TDD check's candidate, never the Engineering check's; a change that introduces structure is the Engineering check's, never the TDD check's (`agents/odin-autonomous.md:217, 227`; `skills/tdd/odin-tdd-workflow/SKILL.md:32-34`; `skills/engineering/odin-engineering-workflow/SKILL.md:30-31`). The one boundary the trigger cannot see — whether the change will need two packages — is caught inside the TDD workflow by the standalone safety stop, which ends the run before any implementation dispatch and names `/yggdrasil/engineer` (§5.2 T-7).

Workflows compose by **staging, not by contract**. An enclosing workflow loads the inner workflow's skill and runs it to completion as one of its own steps, with the inner workflow's gates intact and its Response folded into the enclosing one; no request line and no result line pass between them, and the inner workflow's body does not read which path entered it. The Software Engineering workflow is composed this way twice over: its architecture stage runs the Architecture workflow — context gate, drafting, ratification checkpoint, persistence, and their reviews — and its TDD stage runs the TDD workflow — context gate, plan, plan checkpoint, reviewed packages, integration, and review-gated commits — and the enclosing plan re-ratifies, re-persists, re-plans, re-reviews, and re-commits nothing (`skills/engineering/odin-engineering-workflow/SKILL.md:12, 26, 47-53, 57-62`; `skills/architecture/odin-architecture-workflow/SKILL.md:29, 59`; `skills/tdd/odin-tdd-workflow/SKILL.md:29, 65` — § When to Use, § Workflow step 7; `agents/odin-autonomous.md:223`, generated from `scripts/odin-generator/shared-body.template.md:196`). What the enclosing workflow keeps for itself is the shape verdict over the two optional steps, `Engineering shape: analysis=<yes/no — reason>, architecture=<yes/no — reason>`, and the Response; each stage's checkpoint is a steering point of the enclosing run, and the enclosing cost model names each stage's dispatch count as a term (`odin-engineering-workflow/SKILL.md:24, 35-43, 71`). Both stage-composed workflows are also first-class entry points with a command and a trigger verdict of their own, so composition adds an entry path to a workflow and never a variant of it.
